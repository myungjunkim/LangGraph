## 문제 (agent-19 D2, `[검증]`)

실제 답변이 general-chatbot-api 엔드포인트(`GET /v1/topics`, `GET /v2/gpts/overview`)를 **`https://message-api.qa.hunet.io/docs` 출처로** 인용했는데 **경고가 뜨지 않았다.**

현재 가드(`src/web/app.py:54-67`, `109-112`)는 `extract_urls` / `unverified_urls` 로 **URL 문자열이 이번 턴 도구 결과에 등장하는지**만 본다.
`/docs` URL 자체는 검색 결과에 실재하므로 통과한다. **URL 은 진짜인데 짝이 틀린 경우**를 구조적으로 볼 수 없다.

agent-20 의 `list_api_endpoints` 가 출처 URL 을 직접 제공해 **그 질문에서는** 재현되지 않았지만(Validator 확인), 일반 검색 답변에는 그대로 남아 있다.

## 왜 바로 설계하지 않는가

agent-20·21 은 무엇을 할지 자명했다. **이 건은 다르다.**

- 모델은 출처 제목을 **그대로 쓰지 않고 변형**한다. 정확 일치로 묶으면 거짓 양성이 쏟아진다.
- **틀린 경고는 경고가 없는 것보다 나쁘다.** 사용자가 맞는 답을 의심하게 되고, 곧 경고 자체를 무시하게 된다.
- agent-21 의 교훈: **내가 세운 가정(길이가 주 방어선)이 실측에서 반증됐다.** 여기서 같은 실수를 반복하지 않는다.

→ **1단계에서 실태를 재고, 그 데이터로 2단계 설계를 쓴다.** 규칙을 먼저 정해놓고 데이터를 끼워 맞추지 않는다.

## 1단계 — 실측 (이번 작업)

**산출물은 코드가 아니라 이 문서에 추가될 측정 결과다.** `src/` 를 수정하지 않는다.

### M1. 현재 가드의 정확한 동작
`src/web/app.py` 의 `extract_urls`·`unverified_urls`·호출부(`109-112`)를 읽고, **무엇을 비교하는지/언제 경고가 나가는지**를 코드 근거와 함께 정리한다. CLI(`main.py`)에도 같은 경고가 있는지 확인한다.

### M2. 도구 결과가 제공하는 (제목, URL) 쌍
`src/tools.py` `format_chunks` 의 출력 포맷(`### {title}` / `- source: … | url: …` / 본문)에서 **어떤 쌍을 복원할 수 있는지** 확인한다. `list_api_endpoints`·`call_api`·`system_facts` 결과는 포맷이 다르니 각각 따로 정리한다.

### M3. 실데이터 실태 조사 ★
`data/checkpoints.sqlite` 를 **읽기 전용(`mode=ro`, 사본 권장)** 으로 열어 전수 조사한다.

- 답변(AIMessage) 중 **`출처:` 목록을 가진 것이 몇 건**인가
- 출처 항목의 **표기 형태 분포**: `- [제목](url)` / `- 제목 url` / `- url` / 기타. 각 형태가 몇 건인가
- 각 답변에 대해 **같은 턴의 도구 결과에서 (제목, URL) 쌍을 복원**해 대조하고, 아래로 분류한다:
  1. **정상** — 제목·URL 짝이 도구 결과와 맞음
  2. **오귀속** — URL 은 도구 결과에 있으나 **짝지어진 제목·항목이 다른 출처의 것**(= 이번에 잡으려는 것)
  3. **URL 환각** — URL 자체가 도구 결과에 없음(= 현재 가드가 이미 잡는 것)
  4. **판정 불가** — 변형이 심해 사람이 봐도 모호
- **각 분류의 건수와 대표 사례 원문**을 제시한다. 2번과 4번은 특히 중요하다.
- **현재 가드를 그대로 돌려** 각 답변에 경고가 떴을지 계산하고, 위 분류와 교차표를 만든다(현재 놓치는 건수 = 2번 중 경고 없음).

### M4. 모델이 제목을 얼마나 변형하는가 ★
2단계 설계의 성패가 여기 달렸다.

- 정상(1번) 사례에서 **답변의 링크 라벨**과 **도구 결과의 원본 제목**을 쌍으로 모아, 얼마나 일치하는지 측정한다:
  정확 일치 / 공백·대소문자만 다름 / 부분 문자열 / 전혀 다름 각각 몇 건인가
- **"정확 일치" 비율이 낮다면 제목 대조 방식은 쓸 수 없다.** 그 사실을 분명히 보고해라.

### M5. 후보 규칙의 사전 평가
아래 후보를 **M3 실데이터에 적용해 보고** 거짓 양성/거짓 음성 건수를 각각 보고한다. 구현하지 말고 **측정 스크립트로만** 돌려라(스크래치패드).

| 후보 | 내용 |
|---|---|
| C1 | 답변의 (라벨, URL) 쌍이 도구 결과의 (제목, URL) 쌍 집합에 있는가 (정확 일치) |
| C2 | C1 을 정규화 후 비교(공백·대소문자·마크다운 제거) |
| C3 | 링크 라벨이 **그 URL 을 가진 청크 본문 안에** 등장하는가 |
| C4 | 답변에 언급된 API 경로(`/v1/...`)가 그 URL 의 서비스 청크에 있는가 |

**각 후보의 거짓 양성이 0 이 아니면 그 수치를 반드시 적어라.** 거짓 양성이 있는 규칙은 채택하지 않을 가능성이 높다.

### M6. 경고를 띄울 가치가 있는가
오귀속(2번)이 **실데이터에서 몇 건이나 되는지**가 이 티켓의 존재 근거다.
`[판단 보류]` **건수가 매우 적거나 전부 판정 불가 형태라면, "이 티켓을 하지 않는다" 도 정당한 결론이다.** 그 경우 그렇게 보고해라 — 억지로 규칙을 만들지 마라.

## 2단계 — 설계·구현 (실측 후, 별도 지시)

1단계 결과를 보고 리드가 판단한다. 가능한 결론:
- 거짓 양성 0 인 규칙이 있다 → 명세를 쓰고 구현
- 규칙은 있으나 거짓 양성이 있다 → 경고 문구를 약화하거나(단정 대신 주의) 범위를 좁혀 재검토
- 실측상 빈도가 낮다 → **기각하고 문서에 근거를 남긴다**
